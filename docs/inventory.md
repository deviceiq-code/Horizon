# Inventory (Remarketing)

The physical life of the assets returned at the end of operating leases: from their arrival at a
warehouse to their way out. Source: the business specification "Módulo de Estoque: Recebimento,
Vistoria, Armazenamento e Movimentação" (Nov 2026), delivered in 7 phases.

| Phase | Content | Status |
| --- | --- | --- |
| 1. Foundation | Warehouse codes, locations, containers, asset models, assets and Horizon IDs, labels, movement trail, state machine, movement service, roles | **Done** |
| 2. Appointments and triage | Appointments (receiving and shipping), expected lists, receiving lots, triage of units and accessories, accessory balances, occurrences, reconciliation, closing | **Done** |
| 3. Inspection | Versioned reports, grade code, photos, checklists, findings, penalty table, data erasure tools and certificates (+ the lot's tools per asset class), approval, printable report, part harvesting | **Done** |
| 4. Blocks and disputes | Block follow-ups, disputes, charges, deadline parameters, holidays, aging limits, daily routine, alerts | **Done** |
| 5. Disposal | Stock query, disposals, reservation, picking, shipping, write-off | **Done** |
| 6. Transfers | Transfers between warehouses, virtual transit location, receiving with discrepancies | **Done** |
| 7. Cycle counts and indicators | Counts, adjustments with approval, indicators panel | **Done** |

## Decisions

- **Names in English** (project rule): Asset (Bem), Location (Local), Container (Contêiner),
  MovementEvent (EventoMovimento), AssetModel (Modelo), Warehouse (Armazém).
- **The asset class is the spec's "CategoriaBem"** (penalties, erasure tools per category in
  Phase 3). **Asset models** are a catalog (Administration › Catalogs): manufacturer + model +
  asset class, with the class's specification template values (defaults: no field is required
  on the model), tracking (by unit | by quantity), serial number pattern, kit checklist, test
  script and "has data storage". **Each asset keeps its own specification values**, starting
  as its model's (required fields are completed at inspection).
- **Receiving lots are not per contract**: a customer's return mixes contracts; the contract
  is identified later by the serial numbers (Phase 2).
- **Web on desktop with barcode guns** (keyboard wedge, Enter at the end) — no phone or camera
  support. Scan fields stay focused; every reading answers with a color and a sound.
- **Warehouse code generated by the system**: state (or country) + number, `SP01`, `SP02`,
  `PE01`, `US01` (`inventory/codes.py::next_warehouse_code`). It never changes: location codes
  start with it and are printed on labels.
- **Codes** (`inventory/codes.py`, mirrored in `frontend/src/utils/inventoryCodes.ts`):
  - Horizon ID: `H` + 8 digits + Luhn check digit (`H000012344`), from the PostgreSQL sequence
    `inventory_horizon_id_seq`; it encodes nothing.
  - Container: `C` + 8 digits + Luhn digit, sequence `inventory_container_code_seq`.
  - Location: parent's (or warehouse's) code + `-` + segment (`SP01-EST-03-B`); warehouse,
    parent and segment never change after creation. The global virtual location is
    `VIRTUAL-TRANSIT` (no warehouse).
  - The check digit is verified in the browser and again by the server (RN-15).
- **Label ranges** take consecutive numbers under a PostgreSQL advisory lock (the same lock as
  single IDs), so a range is never interleaved with other IDs. A reserved ID binds to one asset
  only.
- **Labels without new dependencies**: Code 128 (subset B) encoded by a pure function
  (`frontend/src/utils/code128.ts`) and drawn as SVG; one label per 50 × 30 mm page (thermal
  label printers), printed from a hidden frame with the browser's print dialog. No QR code: the
  guns are 1D. The inspection report PDF (Phase 3) will decide on a PDF library.
- **RN-07**: `Asset.status`, `current_location` and `current_container` are written only by
  `inventory/services.py`; the API never writes them (PATCH takes notes and other IDs only).
  Test: `test_status_always_matches_the_latest_event_rn07`.
- **RN-08**: moving a container records one event for the container and one child event per
  asset inside (`MovementEvent.parent_event`), so each asset's history is complete on its own.
  If any asset inside does not fit the destination's area, nothing moves.
- **Events are immutable** (`MovementEvent.save/delete` refuse changes); a correction is a
  `reversal` event (`reverses`) — only an asset's latest event, by a supervisor, with a reason.
- **In transit**: any non-final status may go `in_transit` (to `VIRTUAL-TRANSIT`, keeping
  `status_before_transit`) and comes back only to that status. Nothing goes in transit by a
  plain movement (transfers, Phase 6).
- **Roles** (system roles, Users › Roles): Receiver, Inspection Technician, Storekeeper,
  Inventory Supervisor, Commercial and Finance, Remarketing Analyst; administrators may do
  everything. Movements — receiver, storekeeper, supervisor; containers and label ranges — the
  same; locations — supervisor; reversals — supervisor; appointments — analyst, supervisor;
  lots, triage, occurrences — receiver, supervisor (accepting: supervisor); reading —
  everyone signed in (expected lists: see RN-17). Catalogs (asset models included) follow the other catalogs (everyone
  signed in).

### Phase 2 (appointments and triage)

- **Appointments** (`Appointment`, code `APT-<year>-<NNNN>`): receiving or shipping at a
  warehouse, customer (required for receivings), day and time window, carrier (a service
  provider offering transport, or a name), plate, driver, volumes. Status: scheduled →
  confirmed → in progress → done, or cancelled / no-show (rescheduling brings them back). A
  receiving starts when its lot is opened and is done when the lot closes; shippings are
  started/finished by hand until disposals (Phase 5) take over. **Overlaps in the same
  warehouse are only warned about** (`conflicts`), never refused (decision).
- **Who schedules**: the new system role **Remarketing Analyst** (and supervisors). The
  analyst prepares the **expected list** on the appointment, as agreed with the customer:
  typed into the grid or **pasted from a spreadsheet** (columns Model — "Manufacturer Model",
  or the model alone when only one manufacturer has it —, Serial, Quantity; parsed by
  `inventory/expected.py`, resolved by `POST /appointments/parse-expected/`). No `.xlsx` upload
  (no new dependency).
- **Blind count (RN-17)**: expected lists are read only by analysts, supervisors and
  commercial/finance (`EXPECTED_READERS`); the receivers' API never returns them (the
  appointment omits `expected_items`, `/lots/<id>/expected/` answers 403) and the lot page has no
  such tab for them.
- **Lots** (`ReceivingLot`, code `LOT-<year>-<NNNN>`): opened from a receiving appointment (its
  customer and warehouse) or unscheduled; the dock is read. **Not per contract**: a return mixes
  contracts, identified later by serial number. Status open → reconciling → closed.
- **Triage of units**: label (pre-printed from a range, or empty for a new ID — printed at once),
  model (kept for the next ones), serial (model's pattern, unique per model — RN-05); without a
  serial the reason **and a photo** are required (stored as a lot attachment); "needs to be
  turned on" leaves the serial pending for inspection. Optionally into a container at a dock.
- **Accessories** (models tracked by quantity): `AccessoryBalance` per model + container or
  location + condition good|scrap, never negative (RN-06: check constraint + service);
  damaged ones go to a scrap area. Movement events carry `accessory_model` + `quantity`.
- **Reconciliation** (`inventory/reconciliation.py`, pure): exact serial matches; an expected
  serial under another model → model mismatch; **units without a captured serial stand for
  their model's expected lines** (completed at inspection — decision); unexpected serials fill
  quantity lines, then pair with open serial lines → serial mismatch; the rest → shortage /
  surplus; accessories compare quantities. Running again keeps the same occurrence records,
  removes open ones no longer found and never recreates resolved/accepted ones.
- **Closing (RN-18)**: reconciles again (kept even when closing is refused) and closes only
  with every occurrence resolved or accepted (accepting: supervisors only). The lot's assets go
  to awaiting inspection; putting them in the inspection queue is a movement (also by
  container).
- The Phase 1 manual entry is gone: assets enter through triage only.

### Phase 3 (inspection)

- **Grade code in 3 positions** (decided with Fernando): Conservation A–D (A like new, B light
  marks, C heavy use, D accident or misuse) · Functioning 1 works, 2 with restrictions, 3 does
  not work, 0 not testable · Completeness C complete, P accessory items missing, I essential
  parts missing — e.g. **B1C**. Codes are fixed (`GRADE_CODES`); names and descriptions are
  editable (`GradeLevel`, Remarketing › Inventory Catalogs › Grades). The three values are kept
  separately on the report (for pricing); the asset keeps its current grade
  (`Asset.condition_grade`).
- **Suggestions** (`inventory/grades.py`, pure): functioning from the model's test script (all
  pass → 1, any fail → 2; 3 and 0 are the technician's), completeness from the kit checklist —
  each item is **essential or accessory** (`AssetModel.kit_checklist` = `[{item, essential}]`):
  an essential one missing → I, only accessories → P, none → C. Recommended destination: an
  access block → blocked; does not work and repair not viable → scrap; else available.
- **Reports** (`InspectionReport`): started by reading the asset at a **bench** (the asset goes
  there, IN_INSPECTION); a draft saved at every change; the technician completes a pending
  serial and the asset's own specifications; photos (each asset class lists its required kinds,
  `AssetClass.required_photo_kinds`); findings — automatic ones follow the missing kit items and
  heavy cleaning, manual ones (access block with its type, customization, damage); values from
  the **penalty table** on the report's date (`PenaltyRate`, one table for every customer, no
  overlapping periods — RN-03); supervisors change a value with a justification; without a rate
  a finding blocks the approval (RN-11). Submitting lists what is missing
  (`inspection.problems`). Approval by a supervisor other than the technician (RN-10) sets the
  asset's grade and status (put away later with Movement); an approved report never changes —
  a correction is a new version (RN-09) and the previous one is superseded. Supervisors may send
  a report back with notes. "Mark as sent to the customer" records the date (dispute period —
  Phase 4).
- **Printable report**: the report lives as data; its page is the document — "Print → Save as
  PDF" in the browser (decision: no PDF library).
- **Data erasure**: supervisors set the lot's tool and method per asset class with storage (lot
  page, Data Erasure tab; RN-04); certificates always use them. A model with storage is
  available only after a successful erasure or a removed disk (RN-12); a failure removes the
  disk — a child asset in scrap whose model the technician chooses (RN-13).
- **Part harvesting**: a scrap asset taken apart — unit parts become child assets awaiting
  inspection, quantity parts enter the balance where it is; the asset is written off.

### Phase 4 (blocks and disputes)

- **Deadlines** (`DeadlineSetting`, editable in Inventory Catalogs › Deadlines and Holidays):
  block release 15 calendar days, report dispute 10 business days, dispute analysis 5
  business days, reminders 3 and 1 day before (analysis: 1) — proposed and accepted.
  Business days skip weekends and the registered **holidays** (`Holiday`; the list starts
  empty — decision). Pure calculation: `inventory/deadlines.py`.
- **Access blocks** (`BlockFollowUp`): created when a report with an access-block finding is
  approved. Commercial marks them notified (the deadline starts) and prints a notice per
  customer; records a release the customer reports; a technician checks it — released: a new
  report version (block finding cancelled) and the asset back IN_INSPECTION (erase the data,
  finish); not released: open again. Past the deadline (routine): expired, the finding
  chargeable (RN-20); a supervisor decides parts / scrap (asset → scrap) / other.
- **Disputes** (`Dispute`): only findings of the current approved report **sent to the
  customer**, within `InspectionReport.dispute_deadline` (set when sent — RN-21). Disputed
  findings → disputed, the other approved ones → chargeable, the asset **held** (no new
  version; reservations and transfers will refuse it). Analysis by a supervisor other than
  the report's technician (RN-14): upheld / partially upheld → a new report version approved
  by the analyst with the findings cancelled (the rest chargeable); rejected → chargeable.
  Analysis past its deadline → escalated + alert. No dispute in time → approved findings
  chargeable (routine, RN-22).
- **Charges**: chargeable findings listed per customer; commercial marks them charged (billing
  outside Horizon).
- **Daily routine**: `python manage.py check_deadlines` (cron — see README; supervisors also
  have "Check Deadlines Now"). Idempotent: alerts have unique keys, changes only apply to
  records still in the earlier status.
- **Alerts** (`Alert`: kind + params translated by the UI, for a role or a user, read per user):
  the top bar's bell (unread count, every 3 minutes). Aging alerts use `AgingLimit` (days per
  status; empty = none).

### Phase 5 (disposal)

- **Stock query** (`GET /stock/`): assets grouped by asset class × model × grade × status ×
  warehouse — units, average and longest days in stock (days since the entry, i.e. the triage).
  Filters: status (default available; "all" = every status but written off), warehouse,
  origin customer, asset class, model, grade, minimum/maximum days, search. A group opens to its
  units (`GET /stock/assets/`) with the **current report's data** (functioning, conservation,
  completeness, missing items, entry date, days in stock) and the open disposal holding them —
  the data pricing may use (spec §11); pricing itself is unchanged.
- **Disposals** (`Disposal`, code `DSP-<year>-<NNNN>`; only `inventory/disposals.py` writes
  them): relocation (customer + contract text — contracts live outside Horizon), sale to the
  lessee (customer), **sale to third parties (the buyer is a customer — decision)**, discard
  (a provider offering disposal) and parts (recorded by taking scrap apart — never by hand).
  Optional shipping appointment of the same warehouse: the first picking starts it, the shipping
  finishes it. Status reserved → picking → shipped, or cancelled.
- **Reservation**: an asset read or typed is reserved (AVAILABLE → RESERVED). **Held for a
  dispute, at another warehouse, in another open disposal or in another status → refused.**
  **Scrap assets join discards and stay SCRAP** (the spec's transitions have no SCRAP →
  RESERVED — decision); the open disposal holds them (no other disposal, no taking apart).
  Accessories by quantity (good; scrap only in discards), limited to the warehouse's balances
  minus what other open disposals still have to pick. **Value per unit** on each line
  (decision), the total = Σ quantity × unit value.
- **Picking**: read the shipping area (a SHIPPING area of the warehouse), then each ID: it must
  be on the list (else refused, with a sound) and **moves to the shipping area** (PICKING event —
  decision). Accessories are read from their container or location with a quantity (the
  balance goes down; PICKING event).
- **Shipping** needs every item picked and still in a shipping area, no asset held for a
  dispute (a dispute registered after the reservation blocks it), the document's number and
  file, and for a **discard the destination certificate (RN-23)**. Assets → WRITTEN_OFF
  (SHIPPING events, the last place kept); accessories leave (SHIPPING event with the quantity).
- **Cancelling** (with a reason): picked assets go back to where they were picked from, reserved
  ones are available again (scrap stays scrap), picked accessories return to their balance
  (REVERSAL events). Events of a disposal are never reversed by hand (Movement › reverse refuses
  them). Removing a line is only possible before it is picked.
- **Roles**: commercial/finance, remarketing analysts and supervisors create disposals, reserve,
  set values and cancel (`DISPOSERS`); storekeepers and supervisors pick and ship (`PICKERS`);
  both attach files.

### Phase 6 (transfers)

- **Transfers** (`Transfer`, code `TRF-<year>-<NNNN>`; only `inventory/transfers.py` writes
  them): origin and destination warehouses (different, active), reason, **transit days**
  (default 5, 1–90; beyond them → alert, RN-25), fiscal document (number + file, required to
  send). Status requested → approved → picking → in transit → received | received with
  discrepancy, or cancelled (before sending).
- **Who**: remarketing analysts and supervisors request (items change only while requested);
  **supervisors approve**; storekeepers, receivers and supervisors pick, send, receive and
  finish (`TRANSFER_REQUESTERS`, `TRANSFER_HANDLERS`).
- **What may travel** (decision): available, scrap, blocked and awaiting inspection — never in
  triage, in inspection or reserved; **never held for a dispute** (checked again when picking
  and sending); not in another open transfer or disposal. While in an open transfer an asset
  is not reserved for a disposal nor inspected.
- **Containers** (decision): reading a container stands for all its assets — added together
  (all eligible, or none), picked together (every asset in it must be on the list) and they
  travel in it; the container goes to the virtual location with them and arrives where it is
  read. A container in transit is not moved by hand.
- **Picking (RN-24)**: each ID or container read against the list; a divergence (anything not
  picked, an asset that left its container or is no longer eligible) blocks the sending.
  Accessories are taken from their container or location by quantity (PICKING events).
- **Sending**: assets → IN_TRANSIT at `VIRTUAL-TRANSIT`, keeping the status they left in
  (`Asset.status_before_transit`, `TransferItem.status_before`; TRANSFER_OUT events).
- **Receiving in one step** (decision): read the destination location, then each ID or
  container — back to the status it left in, **there** (RN-02: an available asset goes to a
  stock area, a scrap one to a scrap area; TRANSFER_IN events). Accessories by quantity into a
  container or location of the destination. **Damage is only an occurrence** (decision): the
  asset is received normally and the supervisor decides (e.g. a new report version).
  An asset read that is not on the list is refused and **recorded as a surplus**.
- **Finishing** the receipt: what did not arrive becomes a **shortage** (assets stay in transit
  until found; received later, the shortage is resolved by itself); any occurrence → received
  with discrepancy. Occurrences belong to the transfer (`Occurrence.transfer`) and are
  resolved or accepted as a lot's.
- **RN-25**: the daily routine alerts supervisors once per late transfer (`transfer_late`).
- Events of a transfer are never reversed by hand.

### Phase 7 (counts and indicators)

- **Counts** (`InventoryCount`, code `INV-<year>-<NNNN>`; only `inventory/counting.py` writes
  them): opened by a supervisor — **cyclic** (the locations chosen and everything under them)
  or **general** (every active location of the warehouse); overlapping counts are refused.
- **Locations frozen while counting** (decision): no event moves anything in or out of them
  (`services.check_not_counting`, called by every event except label reprints and the count's
  own adjustments) — movements, picking, receiving, triage, status changes there.
- **Blind readings** (storekeepers, supervisors): read the location, then each asset's ID (read
  again elsewhere: the last reading counts); accessories by model, quantity and condition, at
  the location or in a container there (readings add up). Nothing expected is shown.
- **Closing** compares (`find_divergences`, pure): expected asset not read → **not found**;
  read at another location of the scope → **at another location**; read but recorded outside
  the scope → **not expected here**; accessory quantities different → **balance difference**.
  No divergence → finished at once. The count keeps expected/matched (location accuracy).
- **Adjustments (RN-26)**: each divergence is approved or rejected, always with a reason, by
  a supervisor **who neither counted nor is responsible** for the count (checked in the
  service). Approved: not found → **written off as lost** (decision; INVENTORY_ADJUSTMENT
  event outside the transition table + a LOST occurrence); found elsewhere / not expected →
  the location becomes where it was found (the count is the truth; RN-02 not applied); an asset
  lost by an earlier count comes back in the status it had; balance → set to the count.
  Assets in an open disposal or transfer must be released first. Rejected: nothing changes.
  The count finishes with the last decision.
- **RN-19** (decision: optional): Movement's "Read Origin" switch (remembered with the
  account) adds a first reading — the location where the object is. A different recorded
  location → a LOCATION_MISMATCH occurrence (no lot, transfer or count) + an alert to the
  supervisors; the movement goes on.
- **Occurrences page**: every occurrence (lots, transfers, counts, movements) with filters and
  resolve/accept.
- **Indicators** (`inventory/indicators.py`, `GET /indicators/?from=&to=&warehouse=&customer=`;
  no chart library — decision): lead time arrival → available (by customer, asset class),
  aging by status in bands (0–7, 8–30, 31–90, 91+ days since the last status change), location
  accuracy per count, triage divergences per lot and customer, assets without a serial
  number, conservation by asset class (current reports), blocks released in time, disputes
  upheld, penalties found × to charge × charged × cancelled (current reports), scrap rate.
  Percentages with 5 places, sent as strings.
- ABC classification for counting frequency: left for after the MVP (as the spec allows).

## API (`/api/inventory/`)

`warehouses/` (with `code`), `locations/` (+ `tree/?warehouse=`), `containers/` (+ `reprint/`),
`assets/` (detail with `events`; POST = manual entry; + `reprint/`), `movements/` (POST
`{object_code, destination_code, reason}`; + `<id>/reverse/`), `lookup/?code=`, `label-ranges/`,
`appointments/` (+ `<id>/status/`, `parse-expected/`), `lots/` (POST opens; `units/`,
`accessories/`, `received/`, `expected/`, `reconcile/`, `close/`, `attachments/`),
